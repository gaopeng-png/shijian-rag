# 架构与设计决策

## 数据流

1. `history_events.jsonl` 是唯一人工可审查事件源。
2. 初始化脚本计算内容哈希，以稳定事件 ID UPSERT 到 SQLite，并重建 FTS5。
3. 索引脚本把每个事件及学习资料转换为 Chroma 文档；仅新增、更新或删除内容哈希发生变化的文档。
4. 查询解析器识别年份、事件名、人物、范围和原因/影响/比较等意图。
5. 显式年份和事件名称走确定性检索；模糊问题并行进入人物、FTS5、LIKE 与向量通道。
6. 多通道结果通过加权 RRF 合并。LIKE 只能作为支持证据，避免通用词触发事实回答。
7. 生成器只能使用返回事件构造的上下文。无证据时直接拒答；Qwen 不可用时使用本地模板。

## 为什么采用混合检索

- 年份和专名是结构化条件，向量检索会引入不必要的不确定性。
- FTS5 对明确关键词稳定，向量检索适合没有出现完整事件名的语义提问。
- RRF 不依赖不同检索器分数处于相同区间，适合合并 BM25、规则匹配和向量距离。
- 置信度门控解决“未知年份仍返回最相似事件”和“通用词 LIKE 命中”的错误。

## 索引一致性

- 事件 ID 为 `evt-<sha256(name)[:12]>`，不依赖 SQLite 自增序号。
- 内容哈希包含事件全部可回答字段和来源元数据。
- SQLite 使用 `ON CONFLICT DO UPDATE`，不会因更新而删除再插入记录。
- Chroma 通过公开 `get/delete/add_documents` 接口同步，不读取私有 collection 对象。

## 故障模型

| 故障 | 行为 |
| --- | --- |
| 数据库不存在 | `/api/v1/qa` 返回 503，健康检查为 unhealthy |
| Chroma 未构建 | 精确检索和 FTS5 继续工作，健康检查为 degraded |
| API Key 缺失 | 返回带引用的本地模板答案 |
| Qwen 超时或限流 | 捕获异常并降级，不向用户暴露内部错误或密钥 |
| 本地资料无结果 | 拒绝事实性回答，不调用模型记忆补全 |

## 可观测性

每次请求记录 JSON 日志：`trace_id`、检索模式、召回数、检索/生成/总耗时、Token 数、降级原因和拒答状态。日志不记录 API Key，也默认不记录完整问题和回答。

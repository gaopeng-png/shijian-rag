# 简历项目文案（v1.1.0 发布门禁版）

## 项目名称

史鉴 RAG——面向历史学习的可溯源智能问答系统

## 一句话介绍

基于 Qwen、FastAPI、SQLite 与 Chroma 构建面向历史学习的可溯源 RAG 问答系统，支持混合检索、字段级来源引用、离线评测与模型故障降级。

## 简历要点

- 对 100 条结构化历史事件构建“精确匹配 + SQLite FTS5 + Chroma 向量召回 + RRF 融合”检索链路，使用稳定事件 ID、UPSERT 和证据内容哈希维护索引，返回事件与字段级来源引用。
- 建立 321 条自动回归集和 80 条独立人工评测流程；人工集 Hit@5、MRR@5、来源引用正确率分别达到 `[人工实测值]`、`[人工实测值]`、`[人工实测值]`。（未完成前删除本条数值描述）
- 使用 FastAPI 与 Gradio 提供同进程在线服务，实现模型超时、限流、并发上限、每日 Token 预算和密钥缺失场景的可解释降级，并通过 Docker 与 GitHub Actions 保证可复现交付。

## 当前可证明结果

- 27 项本地测试通过。
- 321 条闭集自动回归：Hit@5 100%、MRR@5 99.84%、拒答准确率 100%、本地检索 P95 7.824 ms。
- 100 条候选证据映射和 20 条双来源结构已完成，但人工已审核数为 0。
- 80 条人工集只有空白槽位，人工指标尚不存在。

自动回归指标可在项目说明或面试中解释，但按 v1.1.0 约定，不把它们包装成简历中的独立人工准确率。完成 `evaluation/HUMAN_REPORT.md` 后再替换占位符。

## 面试准备

- 为什么混合检索优于单一路径，RRF 如何融合不同分数空间？
- 如何区分事件命中、字段证据和来源权威性？
- 为什么 `candidate` 不能计为已审核，内容哈希为何包含证据版本？
- 频率限制、全局并发、Token 预算与硬 429 的边界分别是什么？
- 为什么单机 SQLite 预算账本不适合多副本，生产环境如何迁移到 Redis？
- 如何避免自动生成题目污染独立人工评测？
